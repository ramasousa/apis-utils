Contrato da API de Capital de Giro

Companion do ADR-001. O ADR decide o quê e por quê; este documento especifica como — grafo completo, semântica de idempotência, catálogo de erros, contrato de assincronia, sandbox e política de versionamento.

v1 · 2026-08-31Bradesco-API-Version: 2026-08-31OpenAPI 3.1Uso interno

01Escopo e princípios

Especifica a exposição externa de capital de giro no BaaS. Não especifica motor de crédito, política de risco nem integração com o core — só o contrato que o parceiro vê.

Princípios que ordenam as decisões abaixo

  • O estado é do banco; a visibilidade é do parceiro. Encapsulamos a orquestração, nunca escondemos onde o processo está.
  • Toda resposta ensina o próximo passo. O parceiro não replica a máquina de estado — ele segue o contrato de navegação.
  • Resultado de negócio é estado; falha de chamada é erro. Recusa de crédito nunca é 4xx.
  • Nada obrigatório depende de infraestrutura do parceiro. Integrar sem endpoint público é sempre possível.
  • Todo momento com efeito jurídico é um artefato endereçável, imutável e datado.

02Modelo de recursos

Um ponto de entrada cria o processo. Tudo o mais pende dele. A oferta e a simulação avulsa ficam fora da proposta de propósito — são consultas sem efeito no funil.

# consultas — sem efeito colateral, sem criar proposta GET /capital-de-giro/ofertas?cnpj= → oferta pré-aprovada vigente POST /capital-de-giro/simulacoes-avulsas → comparação; rate limit próprio # o processo POST /capital-de-giro/propostas → 201 + Location + ETag GET /capital-de-giro/propostas/{id} → fonte da verdade · polling GET /capital-de-giro/propostas/{id}/historico → trilha de transições # os passos — artefatos imutáveis pendurados no processo POST /capital-de-giro/propostas/{id}/simulacoes → pode repetir; a última vigora GET /capital-de-giro/propostas/{id}/simulacoes → todas as simulações da proposta POST /capital-de-giro/propostas/{id}/formalizacao → evidência do aceite · CET POST /capital-de-giro/propostas/{id}/assinatura → abre desafio ou devolve link GET /capital-de-giro/propostas/{id}/contrato → PDF assinado · pós-desembolso
Por que sub-recursos e não um POST genérico
Cada URL acima tem um schema de request e response próprio, tipado e nomeado. É isso que faz o gerador de SDK produzir criarSimulacao(propostaId, body: NovaSimulacao): Simulacao em vez de post(body: any): any. O ponto de entrada único continua existindo — é o POST /propostas mais o contrato de navegação. Quem quer simplicidade nunca digita as URLs abaixo dele.

03Grafo de estados

Ponto de atenção — o único estado com dinheiro em trânsito
falha_desembolso não é terminal e não é silencioso. O parceiro precisa distinguir "ainda não caiu" de "não vai cair". Enquanto houver retry interno, o estado permanece com ator: banco; esgotado o prazo, a transição para terminal carrega motivo catalogado e instrução de nova proposta.
Invariante
Recusa de crédito é 200 OK com status: "recusada" e motivo de catálogo fechado. Nunca 4xx. Reprovar é resultado de negócio; 4xx diz ao parceiro que ele errou a chamada — e faz o cliente de suporte dele abrir ticket conosco.

04Contrato de navegação

O bloco estável que sobrevive ao crescimento do grafo. É o que permite adicionar um estado sem quebrar quem já integrou — desde que o cliente seja conforme (§14).

ProximoPasso — presente em toda resposta de proposta. null significa terminal: fim do laço, sem adivinhação.
ProximoPasso:
  type: object
  required: [acao, metodo, href, ator]
  properties:
    acao:
      type: string
      description: Identificador estável da ação. Não é rótulo de UI.
      examples: ["simular", "formalizar", "assinar", "aguardar"]
    metodo: { type: string, enum: [GET, POST] }
    href:
      type: string
      format: uri-reference
      description: URL absoluta ou relativa a chamar. O cliente NUNCA a monta.
    ator:
      type: string
      enum: [parceiro, cliente_final, banco]
      description: |
        parceiro      → chame href com os campos_requeridos
        cliente_final → conduza o cliente ao fluxo indicado em href
        banco         → aguarde; faça polling em _links.self
    campos_requeridos:
      type: array
      items: { type: string }
    expira_em: { type: string, format: date-time }
    intervalo_poll_sugerido_s:
      type: integer
      description: Presente quando ator = banco. Respeitar reduz custo dos dois lados.
Regra de compatibilidade progressiva
Um cliente conforme nunca faz switch exaustivo em status. Ele decide por ator e chama href. Assim, um estado novo introduzido em versão futura degrada para "aguardar" ou "seguir o link", não para exceção não tratada. Isto é requisito de conformidade — está no contrato, não na recomendação.

06Idempotência e concorrência

Duas proteções distintas e complementares. Idempotency-Key protege contra repetição da mesma intenção; If-Match protege contra duas intenções concorrentes. Uma não substitui a outra.

CenárioRespostaComportamento
Retry de rede: mesma chave, mesmo payload201 / 200Devolve a resposta original byte a byte. Nenhum efeito novo. É o caso que impede desembolso duplicado.
Mesma chave, payload diferente422idempotency-key-reutilizada. Sinaliza bug no cliente — a chave é por intenção, não por sessão.
Chave nova, estado já avançou409estado-invalido. O corpo do erro traz o status atual e o proximo_passo correto.
Duas abas do parceiro, mesmo estado, chaves distintas409A primeira vence. A segunda falha no If-Match com versao-divergente. Nenhuma escrita perdida em silêncio.
Requisição original ainda em voo, retry chega antes409requisicao-em-andamento com Retry-After. Nunca processa em paralelo a mesma chave.
Retry após 24h com a mesma chavevariaChave expirou; a proteção passa a ser exclusivamente o If-Match. Documentado para que o parceiro não confie na chave como memória de longo prazo.
Requisito de servidor
A chave é gravada antes de qualquer efeito colateral, num escopo que inclui o parceiro e a rota. Chave replicada entre parceiros distintos nunca colide; chave reaproveitada entre rotas distintas do mesmo parceiro é rejeitada.

07Catálogo de erros

Todo erro é application/problem+json conforme RFC 9457. O type é a chave estável que o parceiro trata em código; title e detail são para humanos e podem mudar.

Formato canônico — proximo_passo viaja no erro quando a recuperação é conhecida. O parceiro não precisa reler para saber o que fazer.
{
  "type": "https://api.bradesco.com.br/problems/versao-divergente",
  "title": "A proposta foi alterada desde a sua última leitura",
  "status": 409,
  "detail": "If-Match informou versao 4; a versao atual é 6.",
  "instance": "/capital-de-giro/propostas/prop_01J8ZK3M4QP7",
  "correlation_id": "corr_8H2K4M",
  "versao_atual": 6,
  "proximo_passo": {
    "acao": "formalizar", "metodo": "POST",
    "href": "/capital-de-giro/propostas/prop_01J8ZK3M4QP7/formalizacao",
    "ator": "parceiro"
  }
}
typeHTTPQuandoAção do parceiro
campos-invalidos422Payload não passa na validaçãoCorrigir. errors[] aponta campo e regra.
consentimento-ausente403Sem base legal vigente para o enriquecimento necessárioRecoletar consentimento e repetir.
estado-invalido409Transição não permitida a partir do estado atualSeguir o proximo_passo devolvido no erro.
versao-divergente409If-Match não corresponde à versão atualReler, reconciliar com o usuário, reenviar.

Não está nesta tabela, e é de propósito
Não existe elegibilidade-negada, credito-recusado nem equivalente. Recusa é estado, não erro. Um parceiro que trata recusa no bloco de exceção constrói a UI errada — e nós construímos o incentivo errado ao devolver 4xx.

08Polling e webhook

Dois caminhos, mesma informação. A paridade não é cortesia: é o que mantém a cauda longa de parceiros integrável e o que nos permite evoluir os eventos sem quebrar quem não os usa.

Polling — caminho padrão

  • GET com If-None-Match devolve 304 quando nada mudou. Resposta sem corpo, sem consumo de cota.
  • Quando ator é banco, a resposta traz intervalo_poll_sugerido_s. Backoff recomendado: 1s, 2s, 4s, 8s, teto 15s.
  • O laço termina quando proximo_passo é null. Não existe condição de parada implícita.
  • Elegibilidade resolve em segundos no caso comum; o desenho não pressupõe polling de horas.

Webhook — otimização opcional

PropriedadeContrato
AssinaturaHMAC-SHA256 do corpo bruto com segredo por parceiro. Header X-Signature: t=<epoch>,v1=<hex>. Tolerância de t: 5 minutos.
EntregaAt-least-once. O parceiro deve deduplicar por event_id.
OrdemNão garantida. Todo evento carrega versao da proposta; evento com versão menor que a última observada deve ser descartado.
RetryBackoff exponencial por 24h em qualquer resposta fora de 2xx. Após 24h, o evento é descartado — e o estado continua disponível por GET.
ConteúdoIdentificador, tipo, versao e status. Nunca dado sensível. O evento é um aviso para reler, não um substituto da leitura.
Regra de paridade — critério de aceite da documentação
Todo evento de webhook tem estado correspondente observável por GET. Nenhuma informação chega exclusivamente por callback. Um parceiro que só faz polling nunca fica sabendo menos — apenas fica sabendo depois. Consequência prática: podemos adicionar eventos sem quebrar ninguém, e a documentação de polling recebe o mesmo investimento da de webhook.

09Sandbox e semeadura de estado

Com máquina de estado, o parceiro não consegue chegar num caminho infeliz só chamando os endpoints na ordem. Sem semeadura, ele descobre expirada e falha_desembolso em produção.

Duas ferramentas: criar já posicionado e forçar transição. Disponíveis apenas no ambiente de sandbox, com a mesma autenticação da API.
POST /sandbox/capital-de-giro/propostas
{
  "estado_inicial": "aguardando_assinatura",
  "cnpj": "00000000000191",
  "simulacao": { "valor": 250000, "parcelas": 12, "taxa_am": 1.79 }
}
→ 201 { "id": "prop_sbx_4K2M", "status": "aguardando_assinatura", ... }

{ "para": "falha_desembolso", "motivo": "restricao_externa" }
→ 200 — qualquer transição do grafo, inclusive as que só o banco dispara

CNPJs determinísticos

Análogo aos cartões de teste de gateways de pagamento: o comportamento é previsível pelo dado de entrada, sem precisar de ferramenta separada.

CNPJ de testeComportamento
00000000000191Sempre aprova. Percorre o caminho feliz completo até desembolsada.
00000000000272Recusa em elegibilidade com motivo: capacidade_pagamento.
00000000000353Aprova, mas a simulação expira em 60 segundos. Exercita o retorno de passo.
00000000000434Assina e falha no desembolso, entrando em falha_desembolso.
00000000000515Elegibilidade lenta — 45 segundos em em_elegibilidade. Exercita o backoff.
Critério de aceite do sandbox
Um parceiro consegue exercitar os nove estados e os seis motivos de recusa sem abrir chamado e sem engenheiro do banco na sala. Se precisar pedir ajuda para produzir um caminho infeliz, o sandbox não está pronto.

10Versionamento

A consequência mais subestimada da decisão do ADR: o contrato passa a ser schema mais grafo. Um estado novo quebra o cliente sem alterar uma linha de JSON.

MudançaClassificaçãoComo entregamos
Campo opcional novo na respostaaditivaImediata, sem nova versão.
Campo novo obrigatório na requisiçãobreakingNova versão datada. Nunca em versão vigente.
Valor novo no enum de statusbreaking por padrãoSó visível para Bradesco-API-Version igual ou posterior. Cliente conforme (§14) absorve sem quebra.
Valor novo no enum de motivobreaking por padrãoMesma regra. Cliente deve ter tratamento genérico de motivo desconhecido.
Transição nova entre estados existentesbreaking por padrãoMuda a sequência que o parceiro observa. Versão datada.
TTL alteradobreaking por padrãoMuda o comportamento observável sem mudar o schema. Comunicação prévia obrigatória.
Remoção de campo ou de estadobreakingDeprecação com headers Deprecation e Sunset. Janela mínima de 12 meses.

A versão é datada e fixada no onboarding do parceiro — Bradesco-API-Version: 2026-08-31. Ausência do header significa a versão fixada no cadastro, nunca a mais recente: nenhum parceiro é promovido de versão sem ato explícito.

12Enriquecimento e base legal

Enriquecimento server-side melhora conversão e destrói explicabilidade — a menos que seja declarado. O parceiro é quem atende o cliente final; sem saber o que foi usado, ele não explica a oferta nem a recusa.

  • Todo campo preenchido pelo banco aparece no bloco enriquecimento com nome do campo, origem e base legal. O valor pode ser omitido; a existência do tratamento, nunca.
  • A origem vem de catálogo fechado — interna, bureau, open_finance. Serve à auditoria e mantém o schema estável.
  • A base legal referencia o artefato concreto — o consentimento coletado pelo parceiro ou o contrato de relacionamento. É o elo que sustenta a cadeia em fiscalização.
  • Consentimento vencido é 403, não silêncio. Degradar a oferta sem avisar é pior que falhar: produz decisão pior sem que ninguém saiba por quê.
  • Formalização é o artefato probatório. Imutável, datado, com CET, taxa, prazo e identificação de quem aceitou. Nenhuma otimização de fluxo pode colapsá-lo em outra transição.
A ser validado antes do congelamento
A cadeia de base legal entre o consentimento que o parceiro coleta e o tratamento que o banco executa precisa de validação jurídica formal — especialmente no arquétipo Headless, em que o titular nunca vê a marca Bradesco durante a coleta.

13Receitas por arquétipo

O mesmo contrato, três consumos. Nenhum deles requer endpoint público.

EmbedUsa nossa tela. Segue o contrato de navegação e ignora as URLs.
let p = await api.post('/capital-de-giro/propostas',
  { cnpj, valor_desejado: 250000 }, { 'Idempotency-Key': uuid() });

while (p.proximo_passo) {
  const { metodo, href, ator, acao, campos_requeridos } = p.proximo_passo;
  if (ator === 'banco') {
    await sleep(p.proximo_passo.intervalo_poll_sugerido_s * 1000);
    p = await api.get(p._links.self, { 'If-None-Match': p.etag });
    continue;
  }
  const payload = await minhaUI.coletar(acao, campos_requeridos);
  p = await api[metodo.toLowerCase()](href, payload,
    { 'Idempotency-Key': uuid(), 'If-Match': p.versao });
}

14Conformidade do cliente

O que um cliente precisa fazer para que a evolução do grafo não o quebre. Publicado na documentação do parceiro e verificado no sandbox antes da liberação para produção.

MUSTDecidir o próximo passo por proximo_passo.ator e href — nunca por switch exaustivo em status.
MUSTTratar status e motivo desconhecidos genericamente, sem lançar exceção.
MUSTEnviar Idempotency-Key nova por intenção e reenviá-la — não regenerá-la — em retry de rede.
MUSTEnviar If-Match com a versao lida em toda escrita, e tratar 409 relendo antes de repetir.
MUSTTratar recusa e expiração como estados de negócio, exibidos ao cliente final — nunca como falha técnica.
MUSTNunca montar URLs de transição por concatenação. Usar sempre o href devolvido.
SHOULDRespeitar intervalo_poll_sugerido_s e usar If-None-Match em todo polling.
SHOULDRegistrar o correlation_id de toda resposta nos próprios logs — é a chave de qualquer investigação conjunta.
SHOULDPersistir o id da proposta antes de qualquer navegação, para permitir retomada após queda.
MAYConsumir webhooks como otimização de latência, deduplicando por event_id e descartando eventos com versao anterior à última observada.
O contrato é bidirecional
Os seis MUST acima são o que nos permite evoluir o grafo sem quebrar o parque integrado. Se não forem verificados no sandbox antes da liberação, a promessa de "adicionar estado sem quebrar ninguém" é falsa — e a Opção A do ADR teria sido a escolha mais honesta.
